# Reproducing the results

Every number, table, and figure in the EIMS paper is regenerated by one of the
scripts in this directory. All analyses use fixed seeds and require no external
data, so a clean run reproduces the published values exactly.

## Setup

```bash
pip install -r ../requirements.txt          # includes the analysis extras
cp ../.env.example ../.env                  # then fill in DB credentials
python -c "import secrets; print(secrets.token_urlsafe(64))"                 # DJANGO_SECRET_KEY
python -c "from apps.core.crypto import generate_key; print(generate_key())" # EIMS_FIELD_KEY
python ../manage.py migrate
```

PostgreSQL is required (the benchmark and figure scripts create and drop their
own throwaway database and never touch deployment data). Figure rendering needs
Chrome or Edge, which the scripts locate automatically.

## What regenerates what

| Paper artifact | Command | Runtime |
|---|---|---|
| **Table II** — functional validation, 89 tests | `python manage.py test apps` | ~1 min |
| **Table III** — weight sensitivity | `python analysis/sensitivity_analysis.py` | ~8 min |
| **Table IV** — predictive validity, plus the dropout-rate sweep | `python analysis/predictive_validity.py` | ~2 min |
| **Table V** — end-to-end performance | `python analysis/benchmark.py --full` | ~25 min |
| **Fig. 1** — system architecture | `python analysis/render_architecture_figure.py` | seconds |
| **Fig. 2** — monitoring dashboard | `python analysis/render_dashboard_figure.py` | ~1 min |
| Manuscript reference/placeholder checks | `python analysis/check_manuscript.py path/to/name.tex` | instant |

`benchmark.py` without `--full` runs the 1k and 10k cohorts only, which takes
about three minutes and is enough to confirm the shape of the results. The 100k
cohort spends most of its time seeding 1.5 million schedule rows.

## Notes on interpretation

**The sensitivity and predictive-validity analyses answer different questions
and, on one point, disagree.** Sensitivity asks whether the ranking is stable
under reweighting; it is. Predictive validity asks whether the ranking is
*accurate*; it is better than chance but the overdue ratio alone scores higher
than the full three-predictor heuristic. Both results are reported in the paper.
Neither is evidence about real immunization behaviour: the forward outcome in
`predictive_validity.py` is simulated, so its absolute AUC values describe the
generative model, not Uganda.

**Performance figures are machine-dependent.** The published table came from a
single-node development machine. Re-running on other hardware will shift the
absolute numbers; what should reproduce is the shape — registration flat in
cohort size, the per-child scoring path linear in round-trips, the set-based
path roughly two orders of magnitude faster, and the dashboard as the dominant
cost at 10^5 children.

**`seed_prototype` is deterministic.** The 20-child cohort behind Fig. 2 comes
from `python manage.py seed_prototype --flush` with a fixed seed, so the
district counts in the figure caption are reproducible byte-for-byte.

## Verifying the security claims

Section VI of the paper binds each control to a test rather than to a checklist:

```bash
python manage.py test apps.core.tests.test_security
```

Seventeen tests, each corresponding to a published sentence — encryption at
rest, blind-index lookup, append-only audit logging, role separation, and
signed expiring artifact links. If one fails, the paper is claiming something
the system no longer does. See `../docs/DEPLOYMENT_SECURITY.md` for the half of
those controls that is deployment configuration rather than application code.
